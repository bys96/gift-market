# Admin 운영 권한 정책

## 1. 목적

Gift Market의 Admin 조회 기능 완료 이후 실제 서비스 운영에 필요한 관리자
권한 범위를 정의한다.

관리자 권한은 크게 다음 두 영역으로 구분한다.

1.  **계정·판매·노출 제어**: 회원 정지, 판매자 영업 정지, 상품 강제 숨김
    등 비교적 안전한 기본 운영 기능
2.  **금전·주문·물류 상태 개입**: 주문 강제 취소, 반품/교환 강제 처리,
    결제 상태 변경, 재고 직접 수정 등 높은 위험도의 기능

기본 원칙은 **낮은 위험도의 운영 제재 기능부터 구현하고, 결제·클레임
workflow에 직접 개입하는 기능은 운영 정책 확정 이후 별도로 설계한다.**

## 3. 1차 구현 권장 범위

현재 Gift Market에서는 다음 운영 제재를 우선 구현한다.

1.  `AdminActionLog`
2.  회원 정지 / 정지 해제
3.  판매자 정지 / 정지 해제
4.  상품 관리자 강제 숨김 / 숨김 해제

------------------------------------------------------------------------

## 4. 회원 정지 / 정지 해제

현재 `UserStatus`는 `ACTIVE`, `SUSPENDED`, `WITHDRAWN`이다.

권장 상태 전이:

``` text
ACTIVE → SUSPENDED
SUSPENDED → ACTIVE
```

`WITHDRAWN → ACTIVE` 관리자 복구는 금지한다.

### 정책

-   악성 사용자 및 어뷰징 사용자를 관리자가 정지할 수 있다.
-   정지 해제가 가능해야 한다.
-   탈퇴 회원을 관리자 기능으로 복구하지 않는다.
-   ADMIN 자기 자신 정지는 금지한다.
-   다른 ADMIN 계정 정지도 우선 금지한다.
-   기존 주문/취소/반품/교환/리뷰 데이터는 유지한다.
-   정지 전에 발급된 JWT가 있어도 보호 API를 계속 사용할 수 없도록 현재
    `UserStatus` 검증이 필요하다.

------------------------------------------------------------------------

## 5. 판매자 정지 / 정지 해제

현재 `SellerStatus`는 `ACTIVE`, `SUSPENDED`, `WITHDRAWN`이다.

권장 상태 전이:

``` text
ACTIVE → SUSPENDED
SUSPENDED → ACTIVE
```

`WITHDRAWN → ACTIVE`는 금지한다.

### 정지 판매자 정책

판매자 정지는 **신규 영업 차단**을 목적으로 한다.

정지 시 제한:

-   신규 상품 등록
-   상품 수정
-   상품 판매 상태 변경
-   신규 판매
-   Buyer 상품 목록/검색에서 해당 판매자의 판매상품 노출

기존 거래 후속 처리는 허용:

-   기존 주문 배송
-   기존 취소
-   기존 반품
-   기존 교환
-   구매자 보호를 위한 후속 처리

핵심 정책:

> **정지 판매자 = 신규 영업 차단, 기존 주문/클레임 처리는 허용**

판매자 정지를 이유로 기존 주문 처리까지 차단하면 구매자 피해가 발생할 수
있으므로 Seller Center 전체를 단순 차단하지 않는다.

------------------------------------------------------------------------

## 6. 상품 관리자 강제 숨김 / 해제

정책 위반, 금지 상품, 허위 상품, 심각한 상품 정보 오류가 발생했을 때
특정 상품만 즉시 노출 차단할 수 있어야 한다.

### 기존 `ProductStatus.HIDDEN`만 사용할 경우 문제

판매자가 직접 숨긴 상품과 관리자가 강제로 숨긴 상품을 구분할 수 없다.
또한 관리자가 `HIDDEN`으로 변경한 뒤 판매자가 다시 `ON_SALE`로 변경할
가능성이 있다.

따라서 관리자 강제 숨김은 판매자 상품 상태와 별도로 관리하는 것을
권장한다.

예시:

``` java
private boolean adminHidden;
private String adminHiddenReason;
private LocalDateTime adminHiddenAt;
```

필요하면 `adminHiddenBy`도 고려할 수 있으나 `AdminActionLog`와 중복
여부를 검토한다.

### Buyer 상품 노출 기본 조건

``` text
Product.status == ON_SALE
AND Product.deletedAt IS NULL
AND Product.adminHidden == false
AND Seller.status == ACTIVE
```

관리자가 숨김을 해제할 때 판매자의 기존 `ProductStatus`를 임의로
`ON_SALE`로 변경하지 않는다. 관리자 제재만 해제하고 실제 판매 여부는
판매자의 상품 상태를 따른다.

------------------------------------------------------------------------

## 7. AdminActionLog

Admin write 기능부터는 관리자 행동 이력을 남기는 것을 권장한다.

최소 구조:

``` text
AdminActionLog

id
adminUserId
actionType
targetType
targetId
reason
createdAt
```

ActionType 예시:

``` text
USER_SUSPENDED
USER_REACTIVATED
SELLER_SUSPENDED
SELLER_REACTIVATED
PRODUCT_HIDDEN
PRODUCT_UNHIDDEN
```

### 목적

-   처리 관리자 확인
-   처리 시각 확인
-   처리 사유 확인
-   CS 및 분쟁 대응
-   관리자 오조작 추적
-   운영 장애 분석

관리자 상태 변경 API에서는 가능하면 `reason`을 필수로 받는다.

------------------------------------------------------------------------

## 8. 취소 / 반품 / 교환 관리자 개입

현재 Admin의 취소/반품/교환 기능은 **조회 전용**으로 유지한다.

관리자 개입 기능은 실제 서비스에서 구현할 수 있지만 단순 상태 변경 API로
만들어서는 안 된다.

### 금지 예시

``` text
PATCH /api/admin/returns/{returnId}/status
status=COMPLETED
```

이 방식은 workflow를 건너뛰어 다음 데이터가 불일치할 수 있다.

-   Payment / PaymentCancellation
-   Order / SellerOrder / OrderItem
-   Shipment
-   Product / Variant stock
-   returnedQuantity
-   canceledQuantity
-   exchangedQuantity
-   restockedQuantity

### 추후 구현 방식

관리자 개입이 필요해지면 상태 변경이 아니라 **운영 행위를 명시한 command
API**로 설계한다.

``` text
POST /api/admin/returns/{returnId}/interventions/approve
POST /api/admin/returns/{returnId}/interventions/refund
```

Admin command 역시 기존 도메인 workflow의 핵심 Service를 재사용해야
한다.

``` text
관리자 중재
→ 기존 도메인 검증
→ PaymentCancellation
→ PG 취소/환불
→ 재고 처리
→ OrderItem 수량 반영
→ SellerOrder 상태 재계산
→ AdminActionLog 기록
```

관리자라고 해서 도메인 invariant를 우회해서는 안 된다.

## 9. 위험도가 높은 기능

### 주문 강제 취소 --- 위험도: 높음

Payment, PaymentCancellation, Order, SellerOrder, OrderItem, Stock,
Shipment가 연계된다. 배송 전/후 정책도 달라질 수 있으므로 현재는
구현하지 않는다.

### 반품 강제 처리 --- 위험도: 높음\~매우 높음

회수 Shipment, 검수, 재입고, 환불, 반품 배송비, PaymentCancellation이
연결된다. CS/분쟁 중재 정책 확정 후 별도 설계한다.

### 교환 강제 처리 --- 위험도: 높음

기존/대상 Variant 재고, ExchangeShippingPayment, EXCHANGE_COLLECTION,
EXCHANGE_OUTBOUND, 검수/재입고가 연결된다. 현재는 조회 전용으로
유지한다.

### 결제 상태 직접 변경 --- 위험도: 매우 높음

구현하지 않는다. DB Payment 상태를 직접 변경하면 실제 PG 상태와 불일치할
수 있다. 실제 결제/취소 결과 또는 reconciliation workflow를 통해서만
변경한다.

### 재고 직접 수정 --- 위험도: 높음

단순 `stock = N` 방식은 주문, 교환 예약, 취소 복원, 반품 재입고 수량과
불일치할 수 있다. 향후 필요하면 별도 **Inventory Adjustment** 개념과
변경 이력을 검토한다.

### 사용자 강제 탈퇴 --- 위험도: 높음

주문, 리뷰, 문의, Seller 등 연관 데이터 처리 및 개인정보 정책이
필요하므로 추후 검토한다.

------------------------------------------------------------------------

## 10. 추후 고려 가능한 운영 기능

### 리뷰 / 문의 숨김 --- 위험도: 낮음\~중간

욕설, 개인정보, 광고/스팸, 정책 위반 콘텐츠 대응용이다. 물리 삭제보다
관리자 숨김 상태와 사유를 별도 관리하는 방향을 우선 검토한다.

### 회원 구매 제한 --- 위험도: 중간

계정 전체 정지까지 필요하지 않은 반복 주문 어뷰징 등에 사용할 수 있다.
현재 규모에서는 회원 정지를 먼저 운영하고 실제 필요성이 생기면 분리한다.

### 판매자 신규 상품 등록 제한 --- 위험도: 중간

판매자 전체 영업 정지보다 약한 제재가 필요한 경우 사용한다. 우선 Seller
`SUSPENDED` 정책을 구현하고 필요성이 확인되면 세분화한다.

### 판매자 정산 보류 --- 위험도: 중간\~높음

정산 기능 구현 이후 검토한다. 금전과 직접 연결되므로 별도 상태, 사유,
AdminActionLog 및 정산 이력이 필요하다.

## 11. 구현 우선순위

### 1차 --- 기본 운영 제재

``` text
AdminActionLog
→ 회원 정지/해제
→ 판매자 정지/해제
→ 상품 강제 숨김/해제
```

이 범위를 Gift Market의 **Admin 기본 운영 제재 기능**으로 정의한다.

### 2차 --- 콘텐츠 운영

필요성이 확인되면:

-   리뷰 관리자 숨김
-   상품 문의 관리자 숨김
-   신고 기능

### 3차 --- CS / 분쟁 중재

실제 운영에서 필요성이 확인된 후:

-   관리자 취소 중재
-   관리자 반품 중재
-   관리자 교환 중재

기존 workflow를 우회하지 않는 별도 command 구조로 설계한다.

### 보류 / 금지

현재 구현하지 않는다.

-   결제 상태 직접 수정
-   클레임 상태 직접 수정
-   임의 재고 수정
-   관리자 강제 탈퇴/복구
-   PG 결과와 무관한 환불 완료 처리

------------------------------------------------------------------------

## 12. 최종 개발 방향

현재 Admin은 회원, 판매자, 상품, 주문, 취소, 반품, 교환 조회와 판매자
신청 승인/거절, Dashboard까지 구현되어 있다.

다음 Admin 개발 범위는 다음으로 제한한다.

``` text
AdminActionLog
→ 회원 정지/해제
→ 판매자 정지/해제
→ 상품 강제 숨김/해제
→ Admin 운영 기능 최종 점검
```

취소/반품/교환 관리자 강제 개입은 현재 범위에서 제외한다.

서비스 운영 이후 실제 CS/분쟁 요구사항이 확인되었을 때 별도 정책과
command workflow로 확장한다.
